01 Project Overview & Goals

SubHero is a multi-service digital top-up platform targeting the Nigerian market. It is part of the SubVerse product suite alongside SubScalp (trading bot) and SubMart (e-commerce). SubHero enables users to purchase VTU services (data, airtime, electricity, cable TV) and SMM services (social media followers, likes, views) from a single wallet-based platform.

Non-Functional Requirements

  • System must handle concurrent transactions without race conditions or double-spending
  • All financial operations must be atomic and idempotent
  • All API endpoints must be authenticated and rate-limited
  • Zero tolerance for wallet balance exploits — every debit/credit is locked at the database level
  • Full audit trail on every financial event — immutable and tamper-evident
  • System must degrade gracefully — failed third-party API calls trigger refunds automatically

03 Security Architecture Overview
⚠️ SubHero handles real money for real users. Every developer on this team must treat security not as an afterthought but as a first-class feature built into every layer of the system. A single exploitable vulnerability can drain user wallets or expose personal data. The architecture below is mandatory — not optional.

Security Layers

LayerWhat It ProtectsMechanisms
Application LayerBusiness logic exploitsInput validation, idempotency, atomic transactions, PIN confirmation
Authentication LayerUnauthorized accessArgon2 password hashing, OTP, session management, brute-force protection
Database LayerRace conditions, double-spendSELECT FOR UPDATE, DB-level constraints, atomic F() expressions
API LayerAbuse, scraping, enumerationRate limiting per IP + per user, CSRF tokens, signed webhooks
Transport LayerMan-in-the-middle attacksHTTPS only, HSTS, TLS 1.2+
Infrastructure LayerServer intrusionUFW firewall, SSH key-only, no root login, Fail2Ban
Audit LayerFraud detection, dispute resolutionImmutable transaction log, IP logging, anomaly alerts

The Golden Rules — All Developers Must Follow

📌
Rule 1: Every wallet debit must use SELECT FOR UPDATE inside an atomic transaction. No exceptions.

Rule 2: Every financial action requires a confirmed, hashed transaction PIN — never trust a session alone for money movement.

Rule 3: Every third-party API call (VTU, SMM, webhook) must use an idempotency key — never process the same event twice.

Rule 4: Never store secrets in code. All API keys, DB passwords, and webhook secrets live in environment variables only.

Rule 5: Log everything financial — every debit, credit, failed attempt, and PIN error — with timestamp and IP address.

Fields Required

Security Measures — Registration
Password Hashing Use Argon2 (Django's most secure hasher). Configure in settings: PASSWORD_HASHERS = ['django.contrib.auth.hashers.Argon2PasswordHasher']
OTP Expiry OTP codes expire in 5 minutes. Store hashed OTP in Redis with TTL=300s. Never store raw OTP in DB.
OTP Rate Limit Max 3 OTP requests per phone number per 10 minutes. Block further requests and alert user if exceeded.
Email Enumeration Return generic response ("If account exists, OTP was sent") — never confirm whether an email/phone is registered or not.
Phone Validation Validate Nigerian phone format server-side with regex: ^(\+234|0)[789][01]\d{8}$. Normalize to +234 format before storing.
Duplicate Prevention Unique DB constraints on both email and phone fields. Check before OTP send, not after.
Registration Rate Limit Max 5 registrations per IP per hour to prevent bot account farming.

Security Measures — Login
Brute Force Protection Lock account for 15 minutes after 5 consecutive failed login attempts. Store attempt count in Redis with TTL. Use django-axes library.
Rate Limiting Max 10 login attempts per IP per minute. Return 429 with Retry-After header on breach.
Session Security Set SESSION_COOKIE_SECURE=True, SESSION_COOKIE_HTTPONLY=True, SESSION_COOKIE_SAMESITE='Lax'. Session expires after 24h of inactivity.
Session Fixation Rotate session ID on every login: call request.session.cycle_key() immediately after authentication.
Concurrent Sessions For MVP: allow. Log all active sessions. Phase 2: single-device enforcement with session invalidation.
Login Notification Send email/SMS alert on new login from unrecognized device or IP (fingerprint by User-Agent + IP).
Timing Attack Prevention Always run password check even if user not found (use check_password on dummy hash). Prevents username enumeration via response time.
AUTH Transaction PIN MVP

Every user must set a 4-digit Transaction PIN during onboarding. This PIN is required to authorize any financial action: VTU purchase, SMM order, wallet funding, or user-to-user transfer. It is separate from the login password.

Security Measures — Transaction PIN
PIN Storage Store PIN as Argon2 hash — never plain text, never reversible. Treat it exactly like a password.
PIN Brute Force Lock financial actions for 30 minutes after 3 wrong PIN attempts. Alert user via SMS immediately on lock.
PIN Reset Require OTP to phone + email confirmation to reset PIN. Log PIN reset events with IP and timestamp.
PIN Validation Timing Validate PIN server-side using constant-time comparison (hmac.compare_digest) to prevent timing attacks.
PIN Expiry on Transactions A PIN confirmation token (generated post-PIN-entry) expires in 60 seconds. Use it as a one-time gate before executing the transaction.
05 Module 2 — Wallet System & Funding

The wallet is the financial core of SubHero. Every user has exactly one wallet. All services are purchased by deducting from the wallet balance. The wallet is funded via a dedicated virtual bank account assigned to each user.

🚨 Critical: The wallet balance field must NEVER be updated with a raw assignment (wallet.balance = wallet.balance - amount). This causes race conditions under concurrent requests. Always use SELECT FOR UPDATE with atomic transactions or Django's F() expressions at the database level.
WALLET Virtual Account Funding MVP

Flow

User views their unique virtual account number
→
User sends bank transfer from any Nigerian bank
→
Providus/Squad webhook fires (POST to SubHero)
→
Wallet credited, user notified

Virtual Account Assignment

  • Each user gets a dedicated static virtual account number (assigned at registration)
  • The account is linked permanently to their SubHero wallet
  • Users can see their account number and bank name on the "Fund Wallet" page
  • Credit the user's wallet with the exact amount received — SubHero absorbs the provider's processing fee as a cost of business
Security Measures — Virtual Account & Webhooks
Webhook Signature Validate every inbound webhook using HMAC-SHA512 signature against the provider's secret key. Reject any request where signature doesn't match. Never process an unsigned webhook.
Idempotency Store the provider's transaction reference in DB with a unique constraint. If the same reference arrives twice (provider retry), return 200 OK but skip processing. This prevents double-crediting a user's wallet.
Webhook IP Whitelist Only accept webhook POST requests from the provider's documented IP ranges. Reject all others with 403.
Webhook Endpoint Privacy Use a non-guessable webhook URL path, e.g. /webhooks/fund/sh-{random-32-char-token}/. Never expose it publicly.
Atomic Credit Wrap the wallet credit inside transaction.atomic(). If any part fails (e.g. notification), the wallet credit rolls back and the webhook is retried by the provider.
Amount Validation Validate that the credited amount is positive, non-zero, and a reasonable number (reject amounts above ₦10 million as suspicious for manual review).
Minimum Funding Enforce a minimum fund amount of ₦100 to prevent wallet spam with micro-transactions.
WALLET Wallet Debit (Purchase Flow) MVP

Safe Debit Pattern — Mandatory for All Purchase Modules

# apps/wallet/services.py — The ONLY approved way to debit a wallet from django.db import transaction from django.db.models import F from .models import Wallet, WalletTransaction def debit_wallet(user, amount, description, reference, order_type): with transaction.atomic(): # Lock the wallet row — prevents race conditions wallet = Wallet.objects.select_for_update().get(user=user) # Check balance AFTER acquiring lock if wallet.balance < amount: raise InsufficientBalanceError("Insufficient balance") # Deduct using F() expression — atomic DB operation wallet.balance = F('balance') - amount wallet.save(update_fields=['balance']) # Write immutable ledger entry WalletTransaction.objects.create( wallet=wallet, amount=amount, transaction_type='DEBIT', description=description, reference=reference, order_type=order_type ) return True
Security Measures — Wallet Debit
SELECT FOR UPDATE Acquire a row-level lock on the user's wallet before reading balance. This prevents two concurrent requests from both reading the same balance and both succeeding on insufficient funds.
Negative Balance Guard Add a CheckConstraint at the DB level: balance >= 0. Even if application code has a bug, the database will reject any debit that would cause a negative balance.
Atomic Rollback If the service purchase fails after wallet debit (e.g. VTU API is down), the transaction rolls back and the wallet is NOT debited. If debited but service fails to deliver, an automatic refund credit is issued.
PIN Gate No wallet debit can occur without prior PIN validation in the same request session. Validate PIN before acquiring the wallet lock.
Decimal Precision Store all monetary values as DecimalField(max_digits=12, decimal_places=2). Never use float for money. Never do arithmetic in Python — use DB-level operations.

Security Measures — VTU Module
Idempotency Key Generate a unique request_id UUID per purchase attempt. Pass it to VTUPass. Store it in DB before API call. If the same UUID appears again (e.g. user double-clicks), reject the second attempt immediately.
Input Validation Validate phone numbers (Nigerian format), meter numbers (format per DISCO), and smartcard numbers server-side before calling the API. Never pass raw user input directly to VTUPass.
Amount Bounds Enforce minimum (₦50) and maximum (₦50,000 per transaction) purchase limits. Reject out-of-range amounts before wallet debit.
Async Execution Execute VTUPass API calls via Celery task — not in the request thread. This prevents timeout-based exploits where users refresh mid-transaction.
Order Status Locking Mark order as PROCESSING before API call. Prevent a second API call for the same order ID. Order states: PENDING → PROCESSING → COMPLETED / FAILED.
Refund Atomicity If API returns failure, credit refund inside the same atomic block as the failure status update. No partial states: either user gets service OR gets refund — never neither.
VTUPass Credential Storage Store VTUPass API key and password in environment variables only. Never hardcode or commit to version control.
Response Verification Always verify the VTUPass response status field. A 200 HTTP status does not mean success — VTUPass returns status codes in the body. Check response.code == "000" for success.
07 Module 4 — SMM Panel

The SMM module allows users to purchase social media growth services (followers, likes, views, comments, subscribers) via the JustAnotherPanel (JAP) API. SubHero buys wholesale and sells at markup. Services are ordered by submitting a URL target and quantity.

SMM SMM Service Catalogue & Orders MVP

Catalogue Sync Strategy

Run a Celery periodic task (every 24 hours) to sync the SMM service catalogue from JAP API. Store services in the SMMService model with SubHero's markup price applied. Admin can toggle any service active/inactive from Django admin.

User browses SMM catalogue by platform
→
Selects service + enters profile URL + quantity
→
PIN confirmation
→
Wallet debited
→
Order submitted to JAP
→
Order ID saved, status tracked

Order Status Polling

A Celery beat task polls JAP every 10 minutes for all orders in PENDING/PROCESSING state and updates their status. Users can see live status on their order history page.

Security Measures — SMM Module
URL Validation Validate that the submitted link is a real, well-formed URL pointing to the correct platform domain (e.g. instagram.com, tiktok.com). Reject any URL containing unusual characters, localhost, internal IPs, or non-matching domains. Use a whitelist of allowed domains per service.
SSRF Prevention Never fetch the user-submitted URL from the server. Only pass it as a string to the JAP API. Never use it in server-side requests that SubHero itself makes. This prevents Server-Side Request Forgery attacks.
Quantity Bounds Enforce per-service min/max quantity bounds as defined in the service catalogue. Reject out-of-bounds quantities before processing payment.
Order Idempotency Generate a unique reference per order attempt. Prevent the same order from being submitted twice if user double-submits.
JAP API Key Storage Store JAP API key in environment variables. Rotate key immediately if suspected compromise.
Markup Integrity SubHero price is calculated and stored at order time — not re-fetched from JAP at payment time. This prevents price manipulation if catalogue sync lags.
Refund on JAP Failure If JAP returns an error on order creation, auto-refund the wallet immediately. If order status becomes CANCELLED after creation, trigger a refund via the wallet credit system.
08 Module 5 — User-to-User Transfers

SubHero users can send wallet balance to other SubHero users instantly and completely fee-free. This is an internal ledger operation — no third-party payment processor is involved. Money moves between SubHero wallets only.

TRANSFER Internal User-to-User Transfer MVP

Flow

Enter recipient (phone number or username)
→
System shows recipient name for confirmation
→
Enter amount + note (optional)
→
Enter Transaction PIN
→
Atomic: debit sender, credit recipient
→
Both users notified instantly

Key Rules

  • Transfers are zero fee for both sender and recipient
  • Minimum transfer: ₦50. Maximum per transfer: ₦100,000 (anti-fraud limit for MVP)
  • Max 10 transfers per user per 24-hour period (anti-abuse limit)
  • Recipient lookup is by phone number or SubHero username — display name before confirmation
Security Measures — User-to-User Transfers
Atomic Double-Entry Debit sender and credit recipient inside a single transaction.atomic() block with SELECT FOR UPDATE on BOTH wallets. Both wallets are locked before any balance change occurs. If either operation fails, both roll back.
Deadlock Prevention Always lock wallet rows in a consistent order (by wallet ID, ascending) to prevent deadlocks when two users transfer to each other simultaneously.
Self-Transfer Block Server-side check: if sender.id == recipient.id, reject immediately. Never allow a user to transfer to themselves.
PIN Requirement Transaction PIN is mandatory for all transfers — no exceptions. Even small transfers require PIN confirmation.
Daily Transfer Limit Enforce maximum 10 outgoing transfers and ₦500,000 total daily transfer volume per user. Check against Redis counter with 24h TTL before processing. Block if exceeded.
Idempotency Key Generate a transfer idempotency key combining sender_id + recipient_id + amount + timestamp-minute. If exact same key seen within 60 seconds, reject as duplicate. Prevents accidental double-tap submissions.
Recipient Confirmation Always display recipient's registered name before PIN entry. Never process transfer to an account without displaying who the money is going to.
Velocity Alerts If a user makes 5+ transfers in under 10 minutes, flag the account for review and optionally require re-authentication before continuing.
Immutable Ledger Create a TransferRecord entry linking sender, recipient, amount, timestamp, and reference. This record is never deleted or updated — only the status field changes (PENDING → COMPLETED).
Minimum Balance Guard After debit, sender's balance must remain ≥ ₦0. DB constraint enforces this independently of application code.

Features

Input Validation & Sanitization

Cross-Platform Input Rules
SQL Injection Django ORM prevents SQL injection by default. Never use raw SQL strings with user input. If raw SQL is necessary, always use parameterized queries: cursor.execute("SELECT * FROM x WHERE id = %s", [user_id])
XSS Prevention Django templates auto-escape all variables. Never use {{ var | safe }} on user-generated content. For rich text, use bleach library with a strict allowlist.
CSRF Protection Django's CSRF middleware is enabled globally. All POST forms include {% csrf_token %}. All HTMX requests include CSRF header via hx-headers.
File Uploads Validate file type by magic bytes (not extension). Restrict avatar uploads to image/* types only. Scan uploads with a content type validator before saving to S3.
Amount Fields Always parse monetary amounts as Decimal from string — never from float. Reject negative values, zero values, and values with more than 2 decimal places at form validation level.

Logging & Audit Trail
